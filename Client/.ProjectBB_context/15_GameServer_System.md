# ProjectBB 服务端与存档边界

## 当前范围

首版验证本地双球对战，不要求登录、完整假后端、账号背包或联网同步。这里只保留边界，尚未实现协议、Server 或存档系统。

ARPG 的账号、装备、主线奖励、摇卡协议以及本地假服状态，不自动成为 ProjectBB 的需求。

## 接入后的依赖

- Protocol 仅含可序列化纯 DTO、协议标识和返回码，不依赖 Unity、Common、GamePlay、View 或 Server。
- Server 保持纯 C#；可依赖 Protocol 和经审查的 LogicCore 纯计算，不调用 Unity、客户端单例、EventCenter 或 ConfigManager。
- GamePlay 不引用具体 Server。业务通过客户端服务入口与传输边界交互。
- 网络管道只负责请求、响应、错误与传输，不实现抽卡、发奖或战斗裁决。
- 本地模拟与远程服务的选择在装配层完成，不在业务中散布本地/联网分支。

具体入口名称和宿主框架待代码确定，不沿用旧文档 API 示例作为事实。

## 状态归属

| 状态 | 归属 |
| --- | --- |
| 当前双球位置、接触、命中、战斗时钟 | 当前 BattleSession |
| 本次肉鸽构筑、阶段、候选选择 | 后续整次肉鸽尝试的运行状态 |
| 账号进度、永久解锁、货币 | 后续账号存档/服务端状态 |
| UI 展示数据 | View 投影 |

整次尝试与单场战斗不能共用一个含义模糊的 RunId。接入服务端时明确各自身份、生命周期和幂等键。

## 权威与验证

- 本地模拟服务有利于验证业务边界，不等于具备防作弊能力。
- 真服务端不能把客户端上传的构筑、奖励或胜负作为天然可信事实。
- 固定步长、固定随机种子和纯几何不等于跨平台逐位确定性；联网帧同步不是首版承诺。
- 接入网络前独立确定战斗权威、同步方式、断线恢复与结果校验方案。
- 存档结构要有版本和升级策略；未实现前不承诺兼容 ARPG 存档。
- 客户端持久化和数据保护需求随具体小游戏平台确定。
